# DEVNIRA — One workflow for the four remaining components

Run manually: [four-component-build.yml](../.github/workflows/four-component-build.yml).

The workflow evaluates the four tracks **in parallel**, records the actual development build outcomes, and then always runs a **fail-closed production gate**. Its red release-gate job is intentional as long as evidence is missing. **Do not change the release gate to green by substituting mock evidence.**

| Track | What this workflow really verifies | What is STILL required before launch |
| --- | --- | --- |
| Active ZK circuit/prover/verifier | Compiles V2 amount prototype in upstream `qp-wormhole-inputs` | V2 Poseidon2 leaf, prover, verifier, aggregation, real valid/invalid withdrawal proofs |
| DVN runtime + genesis | Compiles patched rewards/vesting in upstream 12-decimal node and WASM | Fully migrated 8-decimal runtime, enforced 100M total supply, independent genesis funded using approved public beneficiary keys, fees and 3M liquid / 7M locked |
| Windows wallet | Packages a read-only local-RPC node monitor as an EXE | Secure audited keys, valid DVN address format, signed send/receive, reliable balances and vesting display |
| GPU mining testnet | Verifies QPoW reward formula reference | Real NVIDIA/AMD GPU miners, two-node sync, PoW validation, chain reorg and reward/cap tests |

The approved immutable economic targets: 100M DVN total, 90M mined, 10M founders/investors/team, 3M immediately accessible, 7M released in 12 **calendar-month** instalments. Node identity must be independent of Quantus. No wallet seed/private key is ever required in GitHub.

A **verified public wallet address and beneficiary split** are required inputs to create *real* genesis balances. No fake recipient addresses are used. The development node's existing genesis does NOT allocate actual DVN coins.

The current workflow is a **candidate integrator**, **not a complete one-command mainnet builder**. It is intentionally manual-only to avoid repeatedly consuming 30–60 minutes of CI on every small code commit. No workflow can establish NVIDIA/AMD hardware compatibility on a runner with neither GPU. No workflow can certify cryptographic security from arithmetic unit tests.

## Completion condition

The project is *not finished* until a pinned, reproducible 8-decimal DVN native+WASM runtime with a DVN-only independent genesis, matching Poseidon2 leaf/proof/verifier circuit, secure Windows signing wallet and multi-node actual GPU mining testnet have all passed recorded integration and adversarial tests. `scripts/release_evidence_gate.py` rejects missing individual evidence. Even when it passes, a separate security review is needed.

## Approved single-company beneficiary policy — 2026-10-13

The founder/team/investor allocation is assigned to ONE company-controlled DEVNIRA public wallet (not split across separate founder/investor wallets). Exact amounts: **3,000,000 DVN liquid at genesis**, **7,000,000 DVN locked and released in 12 Gregorian calendar-month instalments**. `config/genesis-proposal.json` stores this intent under `company_treasury`, deliberately leaving `public_address: null` until a genuine independent DVN signing wallet and network address format have been developed and the company-controlled public account has been verified. **Do not use a mock or Quantus dev account as the company beneficiary.**

The exact single-beneficiary, 12-grant manifest is generated by `spec/company_treasury.py` and tested in `tests/test_company_treasury.py`. The combined CI validates this policy but explicitly **does not mint real coins**. A caller's `address_verified=True` flag is only an externally asserted precondition; the manifest generator does *not* independently validate an SS58 address or ownership. The on-chain genesis and signing wallet remain open requirements; never commit private keys, mnemonic phrases or seed material.

Once an actual DVN wallet exists, obtain only the public receive address and verify control of that account offline before freezing the independent genesis. A simple GitHub green check is not evidence of custody.

## Wallet network-identity safety module (2026-10-13)

`wallet/network_identity.py` now includes a strict localhost-RPC URL validator and rejects upstream-Quantus chain/runtime names and mismatched genesis hashes. `tests/test_network_identity.py` covers hostile/malformed URLs, foreign network names and incorrect genesis pins. The four-component Windows job now runs these unit tests.

**This is a prerequisite library, not yet wired into the Tkinter monitor's refresh action.** Until the native DEVNIRA signing wallet and independently verified genesis hash exist, the monitor is read-only and must not be described as secure company custody. In particular, passing the network-identity unit tests does not create keys or prove trusted chain ownership. The approved single-company beneficiary account remains `null` in the proposal.

## Actual Plonky2 V2 amount range constraint candidate — 2026-10-13

`scripts/patch_zk_leaf_amount_v2.py` now injects a **real Plonky2 circuit gadget** into `qp-wormhole-circuit` source, enforcing 54-bit input range AND the exact 100,000,000 DVN native total-supply upper bound for a single field-element amount. It also includes a positive proof/verify and negative proving test (100M+1 base units must fail). `.github/workflows/zk-proof-input-v2.yml` builds this circuit crate together with the independent V2 input codec. The gadget is opt-in, **not active in production leaf or aggregator**; no verified CI result exists for the new proof test yet.

`scripts/patch_dvn_runtime_units.py` prepares **actual runtime identity and 8-decimal balance constants**, but intentionally **refuses** to apply while the old u32/10^10 ZK tree and Wormhole scaling remain present, or reward/immutable-vesting patches are absent. Regression tests verify all these fail-closed conditions and the exact staged 8-decimal runtime constants. `four-component-build.yml` exercises this negative safety check, rather than silently producing an unusable eight-decimal chain.

**Still blockers, not solved by passing candidate compilation:** active leaf-format and witnesses, exact prover/aggregator/verifier/public-input migration, native assets vs foreign-assets policy, coherent fee/quantum logic, trusted independent genesis, company-controlled secure signer, real GPU PoW hardware tests. Do not interpret the expected old-ZK rejection as a successful 8-decimal native node build.

## Single-workflow V2 proof and two-node test additions (2026-10-13)

The combined workflow now runs the DEVNIRA native amount Plonky2 circuit proof/verify tests directly against the upstream `qp-wormhole-circuit` source **in the same job as the V2 proof input crate**. The positive test accepts 0, 1 base unit, 5 DVN and the maximum 100M DVN base units; oversized witnesses must fail. These are genuine gadget-level proofs, NOT an active ZK leaf/aggregated withdrawal proof.

`scripts/test_two_node_rpc.py` is an executable, independent DEVNIRA **two-node smoke harness**: it requires two distinct localhost RPC endpoints, an independently pinned trusted DEVNIRA genesis hash, DEVNIRA runtime identity, peers on both nodes, finalized chain advancement and the same block hash at the minimum common finalized height. `tests/test_two_node_rpc.py` exercises wrong genesis, peers, stalled finality and fork rejection; the combined CI runs this **test suite only** because it lacks a truly independent DVN genesis and two running DVN nodes. Once independent nodes exist, run e.g.:
```bash
python3 scripts/test_two_node_rpc.py \
  --node-a http://127.0.0.1:9944 \
  --node-b http://127.0.0.1:9945 \
  --trusted-genesis 0x<64-trusted-hex-digits>
```
The sample is a placeholder; it is not a real chain hash. The smoke harness does **not** verify NVIDIA/AMD proof generation or QPoW validity and must never satisfy those release-evidence fields by itself.

**State:** Both files and workflow updates are committed, but the new combined CI run outcome was not established in this change. Independent Genesis, actual ZK circuit migration, wallet signing, GPU hardware tests and security review still block production.

## CI status presentation corrected after build #2

Build #2 showed all **four candidate jobs green** while the workflow as a whole was red solely because the last job deliberately ran `scripts/release_evidence_gate.py` against an empty JSON object. This did **not** indicate a compilation failure. The workflow now has `candidate-summary`: it **fails** when any of the four candidate jobs failed or were skipped, but runs the release-evidence script as an **informational audit** when the production requirements are absent. It uploads `production-blockers.txt` and prints **Production: BLOCKED** in the GitHub job summary. The standalone `production-build.yml` production-source gate still fails closed if the actual chain is incomplete.

This does not upgrade the project's mainnet status. A green four-component development workflow only means four development jobs and their defined tests passed. It does not certify active ZK proof integration, secure custody or physical GPU mining. A regression test in `tests/test_four_component_ci_status.py` protects this distinction.
